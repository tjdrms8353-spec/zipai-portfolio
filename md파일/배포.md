# ZipAI 개인 포트폴리오 배포 작업 기록

## 기록 원칙

- 이 문서를 개인 배포 작업의 누적 기록으로 사용한다. 배포 관련 작업을 수행할 때마다 날짜, 요청·결정, 실제 변경, 검증 결과, 남은 작업을 추가한다.

## 현재 배포 방향

2026-10-06 변경 결정: 사용자는 원본 이력을 개인 main에 유지하는 대신 새 첫 커밋으로 시작하기로 했다. 이전 기록의 이력 보존 방침을 변경하며, 팀 프로젝트 출처·기여자 표기와 로컬 원본 백업을 유지한다.

비용 기준: 무료·최소 비용 우선. EC2와 RDS 도입은 당장 진행하지 않는다. 각 서비스의 무료 범위와 사용량에 따른 비용은 실제 계정에서 확인한다.

| 항목 | 담당 역할 |
| --- | --- |
| 본인 GitHub | 팀 이력을 보존한 코드 관리, 본인 기여와 개인 개선 내역 공개 |
| 본인 TiDB | 팀 DB와 독립된 개인 데모용 DB |

실행 순서: 개인 GitHub → 개인 TiDB·데모 데이터 → 개인 Render 연결 → S3 연동 → Netlify 소개 페이지 → 기능 검증.

## 2026-10-06 — Render 우선 배포 방법 안내

### 요청·결정

- 사용자가 Render에 먼저 배포하는 방법을 요청했다.
- 개인 GitHub와 개인 TiDB를 연결한 Docker Web Service의 수동 생성 절차를 안내한다. Netlify·S3 연동은 후속 작업이다.
- 기존 `render.yaml`에는 세 OAuth 제공자가 모두 활성화되어 있어, 처음에는 Blueprint 대신 Web Service 화면에서 사용할 설정만 직접 입력하는 방식으로 안내한다. Web Service 수동 생성은 `render.yaml` 환경변수를 자동 적용하지 않는다.

### 1. 배포 전 준비

- 개인 GitHub 저장소의 배포 브랜치에 `Dockerfile`, `build.gradle`, `settings.gradle`, `gradlew`, `gradle/`, `src/`, `templates/`, `static/`, `index.html`, `rpa/lifestyle_ml/`가 있어야 한다.
- 개인 TiDB 클러스터와 `zipai` DB를 준비하고 Connect 화면에서 호스트·포트·사용자명·TLS 연결 안내를 확인한다. 로컬 MySQL의 `localhost` 주소는 Render에서 사용할 수 없다.
- 빈 DB로 시작하면 애플리케이션의 Flyway가 테이블을 생성한다. 업무 데이터 이전은 별도이며 마이그레이션 성공을 배포 로그에서 확인한다.
- 이미 본인 소유이며 개인 저장소·개인 DB에 연결된 Render 서비스가 있다면 중복 생성하지 않고 해당 서비스를 사용한다. 팀 공용 서비스는 개인 배포용으로 변경하지 않는다.

### 2. Render Web Service 생성

1. https://dashboard.render.com/ 에 본인 계정으로 로그인한다.
2. `New` → `Web Service` → `Git Provider`에서 본인 GitHub를 연결한다.
3. 개인 저장소를 선택하고 아래 값을 설정한다.

| 설정 | 입력값 |
| --- | --- |
| Name | 사용 가능한 개인 서비스 이름. 예: `zipai-본인영문아이디` |
| Branch | 실제 배포 코드가 있는 브랜치. 보통 `main` |
| Language / Runtime | `Docker` |
| Region | 선택 가능한 리전 중 TiDB와 가까운 리전 |
| Root Directory | 비워 둠: 저장소 루트 사용 |
| Dockerfile Path | `./Dockerfile` |
| Docker Build Context | 해당 항목이 있으면 `.` |
| Docker Command | 비워 둠: Dockerfile의 ENTRYPOINT 사용 |
| Instance Type | `Free` |

Dockerfile이 빌드와 실행을 처리하므로 별도의 Gradle Build Command나 Start Command를 입력하지 않는다.

### 3. 환경변수 입력

Render Environment 설정에 아래 값을 입력한다. 값의 앞뒤에 따옴표를 붙이지 않는다.

| 변수 | 입력 내용 |
| --- | --- |
| `DB_URL` | 본인 TiDB JDBC URL. 아래 예시의 호스트·포트·DB 이름을 실제 값으로 변경 |
| `DB_USERNAME` | TiDB Connect 화면의 전체 사용자명 |
| `DB_PASSWORD` | 본인 DB 비밀번호 |
| `KAKAO_OAUTH_CONFIGURED` | 첫 기동 시 `false` |
| `NAVER_OAUTH_CONFIGURED` | 첫 기동 시 `false` |
| `GOOGLE_OAUTH_CONFIGURED` | 첫 기동 시 `false` |

```text
jdbc:mysql://YOUR_TIDB_HOST:4000/zipai?sslMode=VERIFY_IDENTITY&serverTimezone=Asia/Seoul&characterEncoding=UTF-8
```

포트·TLS 옵션은 본인 TiDB Connect 안내를 우선한다. 인증서 오류가 발생하면 해당 클러스터의 Java 신뢰 저장소·CA 설정을 확인하고 TLS 검증을 끄지 않는다. 소셜 로그인 키는 준비되었을 때 추가하며, 최초 설정에서는 빈 CLIENT_ID/SECRET 변수를 만들지 않는다.

기능 활성화 시 추가할 값:

- `VWORLD_API_KEY`: 지오코딩에 사용할 본인 키.
- `PROPERTY_IMPORT_TOKEN`, `FINANCE_IMPORT_TOKEN`: 개인 수집 작업과 일치하는 서로 다른 임의의 긴 토큰.
- 사용할 제공자의 `KAKAO_OAUTH_CLIENT_ID`/`KAKAO_OAUTH_CLIENT_SECRET`, `NAVER_OAUTH_CLIENT_ID`/`NAVER_OAUTH_CLIENT_SECRET`, `GOOGLE_OAUTH_CLIENT_ID`/`GOOGLE_OAUTH_CLIENT_SECRET`. 준비한 제공자만 `*_OAUTH_CONFIGURED=true`로 변경한다.

현재 서버 설정은 `${PORT:8080}`을 사용하므로 Render가 제공하는 PORT를 따른다. PORT를 임의로 변경할 필요는 없다.

### 4. 배포와 확인

1. `Create Web Service` 또는 생성 화면의 배포 버튼을 누른다.
2. Deploys/Logs에서 Docker·Gradle 빌드, DB 연결, Flyway 마이그레이션, Spring 기동 순서로 확인한다.
3. `Live`가 표시되면 발급된 HTTPS 주소에서 메인 화면, CSS·JS, 회원가입·일반 로그인, DB 조회를 확인한다. 빈 DB에서는 업무 데이터가 없을 수 있다.
4. 지도 제공자 콘솔에 개인 배포 URL을 등록한다. 소셜 로그인은 실제 서비스 주소의 `/login/oauth2/code/kakao`, `/login/oauth2/code/naver`, `/login/oauth2/code/google` 중 사용할 콜백을 등록한다.
5. 코드 수정 후 개인 저장소에 push하고, 자동 배포가 꺼져 있으면 `Manual Deploy` → `Deploy latest commit`으로 재배포한다.

오류 점검:

- DB 연결 실패: JDBC URL·전체 사용자명·비밀번호·TLS·TiDB 네트워크 접근 정책을 확인한다.
- Flyway 실패: 최초 원인과 대상 스키마·이력을 확인한다. 검증을 끄거나 DB를 삭제해 우회하지 않는다.
- 지도 인증 실패: 지도 키와 허용된 사이트 URL을 확인한다.
- 프로세스 종료·메모리 오류: 실행 로그와 메모리 사용량을 확인한 뒤 JVM 설정 또는 인스턴스 구성을 조정한다.

Render 무료 서비스는 유휴 중지와 임시 파일시스템 제한이 있다. S3 연동 전 업로드 파일의 영속성은 확보되지 않는다. Python 추천 기능도 별도 실행 검증이 남아 있다.

### 수행·검증 범위

- Render Docker/Web Service 공식 문서와 TiDB JDBC 안내를 확인하고 프로젝트 설정에 맞춘 배포 절차를 기록했다.
- 이번 작업은 방법 안내와 문서 수정이다. 실제 계정 연결·환경변수 등록·빌드·배포·접속 검증은 수행하지 않았다.

## 2026-10-06 — GitHub 업로드와 실행·디버그 구분 안내

### 요청·결정

- 사용자가 GitHub에 먼저 올리려고 VS Code의 실행 및 디버그를 눌렀으며, 표시된 디버거 중 무엇을 선택하는지 질문했다.
- 해당 메뉴는 로컬 실행용이다. GitHub 업로드 목적이면 선택하지 않고 Esc로 닫은 뒤 소스 제어(Ctrl+Shift+G)를 사용하도록 안내했다. Java는 로컬 Java 실행·디버깅을 할 때 선택하는 항목이다.

### 확인 결과

- `git remote -v`: 현재 origin은 `https://github.com/tylyoon/zipai-integrated.git`이다. 이 계정이 사용자 본인인지 팀 계정인지 아직 확인하지 않았다.
- 현재 브랜치는 `main`이다.
- `git status --short`에서 `bin/`, `wake.bat`, `zipai-full.sql`이 미추적 상태다. DB 덤프를 포함한 전체 파일 일괄 커밋은 하지 않도록 안내한다.
- 개인 계정이 현재 원격 저장소 소유자와 다르면 개인 저장소를 준비하고 별도 원격 연결을 설정한 뒤 push해야 한다.

### 수행·검증 범위

- Git 원격·브랜치·작업 상태를 읽기 전용으로 확인하고 VS Code 공식 소스 제어 문서를 참고했다.
- 커밋, push, 원격 변경, 실제 배포는 수행하지 않았다.
- 다음 단계에 필요한 정보: 본인 GitHub 아이디 또는 개인 저장소 URL.

- `main`의 기존 팀 브랜치 추적 설정을 해제했다. 개인 저장소에 처음 push할 때 `git push -u origin main`으로 개인 브랜치를 추적하도록 설정한다.
- `.git` 쓰기 제한으로 승인된 명령을 사용했다. Git의 드라이브 소유권 확인 오류는 해당 명령에만 `safe.directory=E:/zipai-integrated`를 지정해 처리했다. 전역 Git 설정은 변경하지 않았다.

### 검증 결과

- `git remote -v`에서 개인 origin과 팀 upstream을 확인했다.
- `git branch -vv`에서 main의 기존 원격 추적 해제를 확인했다.
- 커밋과 GitHub push는 수행하지 않았다. 현재 연결된 주소만 변경되었으며 개인 GitHub에 코드가 업로드된 상태는 아니다.

### 다음 단계

- 게시할 기존 코드·이력에 비밀값이 없는지 점검한 뒤 `git push -u origin main`으로 기존 커밋을 개인 저장소에 업로드한다.
- `bin/`, `wake.bat`, `zipai-full.sql`은 미추적 상태이므로 일괄 추가하지 않는다. 특히 SQL 덤프를 공개 저장소에 올리지 않는다.
- 이 배포 문서는 현재 Markdown 제외 규칙 때문에 Git 미추적 대상에서 제외되어 있다. 문서 게시를 위한 예외 설정과 커밋은 별도 작업이다.

## 2026-10-06 — 사용자 Push 오류와 GUI 업로드 안내

### 확인한 상태

- 사용자가 기존 PowerShell 터미널에서 `git push -u origin main`을 실행한 화면을 제공했다.
- 작업 경로는 `E:\zipai-integrated`로 올바르다. 기존 터미널 사용은 문제가 아니다.

- 앞서 적용한 명령별 safe.directory 설정은 지속적인 사용자 Git 설정이 아니므로 사용자 터미널·GUI에서는 동일한 오류가 발생할 수 있다.

### 안내 내용

- 실행 및 디버그는 프로그램 실행 기능이며 GitHub 업로드에는 VS Code 소스 제어 또는 GitHub Desktop을 사용한다.
- VS Code: Ctrl+Shift+G → 저장소 안전 경고의 Manage Unsafe Repositories → 본인 프로젝트 `E:\zipai-integrated`만 안전한 저장소로 지정 → 소스 제어 메뉴의 Push to...에서 개인 origin 선택. 최초 upstream 설정 확인이 나오면 개인 origin/main을 대상으로 지정한다.
- GitHub Desktop: 본인 계정 로그인 → File / Add local repository → `E:\zipai-integrated` 추가 → Repository Settings / Remote에서 개인 origin 확인 → main의 Publish branch 또는 Push origin 사용.
- GitHub Desktop에서도 소유권 오류가 발생하면 해당 저장소의 Git 신뢰 설정을 해결해야 한다. 프로그램 변경만으로 오류가 사라진다고 보장하지 않는다.
- 기존 커밋 업로드를 위해 미추적 파일까지 새로 커밋할 필요는 없다. `zipai-full.sql`을 선택하거나 전체 변경을 일괄 커밋하지 않는다.

### 수행·검증 범위

- 사용자 스크린샷과 VS Code·GitHub 공식 문서를 기준으로 안내했다.
- 이번 작업에서 Git 신뢰 설정 변경, 커밋, Push는 수행하지 않았다.
